# M7 — Plus

Status: **in progress** (server and app built; waiting on CI, the owner's RevenueCat and App Store Connect setup, and a TestFlight purchase)

## Scope

From SPEC.md §2 and §6: RevenueCat for purchases and price experiments, the server knowing who
has Plus, Squad Boost, streak freezes, and the three paywall moments. The paywall already exists
(M1, StoreKit 2); M7 makes Plus real end to end.

Done when: a TestFlight sandbox purchase unlocks Plus in the app and on the server within a few
seconds (squad limits, custom lengths, Plus cosmetics, Deep Focus once approved), a refund or
expiry takes it away, Squad Boost shows on a squad with one Plus member, and a missed day spends a
freeze instead of breaking the streak.

## Purchases

- **RevenueCat SDK** (`purchases-ios-spm`) behind `PlusStore`, configured with the public API key
  from the build (`LK_REVENUECAT_KEY` in `Config/Local.xcconfig` / a CI secret). With no key the
  store keeps using StoreKit 2 directly, so builds without RevenueCat still work.
- `appUserID` = the server's user id once signed in (`Purchases.logIn`), anonymous before; signing
  out calls `logOut`.
- Products (App Store Connect, owner): `lockin.plus.monthly` A$3.99, `lockin.plus.yearly` A$24.99
  with a 7-day trial, `lockin.plus.lifetime` A$49.99 (non-consumable). RevenueCat entitlement
  `plus`; offering `default` with those three packages.

## Server

| Route | Body | 200 | Errors |
|---|---|---|---|
| `POST /webhooks/revenuecat` | RevenueCat's event | 200 | 401 without the shared `Authorization` value |
| `POST /me/plus/refresh` | | `{ user }` (asks RevenueCat's REST API for the caller, sets `plus_until`) | 503 `try_again` |

- Webhook events set `users.plus_until`: `INITIAL_PURCHASE`, `RENEWAL`, `PRODUCT_CHANGE`,
  `UNCANCELLATION`, `NON_RENEWING_PURCHASE` (lifetime → year 9999), `EXPIRATION`,
  `CANCELLATION` with a refund (→ now), `TRANSFER` (moves Plus between our user ids). Unknown
  `app_user_id`s (anonymous) are ignored. Secrets: `REVENUECAT_WEBHOOK_AUTH`,
  `REVENUECAT_SECRET_KEY`.
- **Squad Boost**: a squad with any Plus member is `boosted: true` in `GET /squads`; boosted pets
  can wear premium pet accessories (`fixtures/shop/catalogue.json` part `pet`), chosen by any
  member, shown to everyone (`p.k` gains an accessory: `"sprout.2.a3"`; `PetCode` already ignores
  what follows the stage).
- **Streak freezes**: each Plus member gets 2 a month (calendar month, squad time zone). When a
  squad's last counted day is the day before yesterday and a Plus member has one left, the gap day
  is filled with that member's freeze instead of the streak breaking (at most one gap per check).
  `streak` in `GET /squads` gains `frozenDays: ["YYYY-MM-DD"]` for the last 30 days, and `freezes`
  for the caller.

## App

- Paywall moments: (1) after the first completed squad session (once), (2) creating a second
  squad or adding a 5th member (the 402 `plus_required`), (3) tapping a Plus cosmetic, custom
  length or Deep Focus. Never at launch; never blocking a session.
- Settings: Plus status, Manage subscription (`showManageSubscriptions`), Restore.
- Squad detail: the Boost badge and the pet accessory picker for boosted squads; the streak shows
  frozen days with a snowflake.
- Custom session lengths (Plus): a stepper on Home's length picker, 5–240 minutes.

## Owner

RevenueCat project (App Store app, products, entitlement `plus`, offering `default`, webhook to
`https://<api host>/webhooks/revenuecat` with an Authorization value), App Store Connect
subscription group and products with prices, tax and banking agreements, sandbox testers.

## As built (server)

Details the app relies on, settled while building the Worker (499 server tests, with Demo Buddy and
gentle slips). The contract above holds; everything here fills in what it left open.

**Routes**

| Route | Body | 200 | Errors |
|---|---|---|---|
| `POST /webhooks/revenuecat` | RevenueCat's `{ api_version, event }` | `{ ok: true, result }` | 401 `unauthorised` (the `Authorization` header isn't exactly `REVENUECAT_WEBHOOK_AUTH`, constant-time compare), 503 `not_configured` (secret unset), 400 (no `event.id`/`event.type`) |
| `POST /me/plus/refresh` | | `{ user }` | 503 `not_configured` (no `REVENUECAT_SECRET_KEY`), 503 `try_again` |
| `PATCH /squads/:id/pet` | `{ accessory: 1–6 \| null }` | `{ squad }` | 403 `not_member`, 422 `accessory_invalid`, 402 `plus_required` with `limit: "boost"` |

**The webhook** (`src/plus.ts`)

- Our user is the first of `app_user_id`, `original_app_user_id`, then `aliases` that is one of our
  10-character ids (people only; Demo Buddy never gets Plus). Anonymous (`$RCAnonymousID:…`) and
  unknown ids: `result: "ignored (nobody of ours)"`.
- `INITIAL_PURCHASE`, `RENEWAL`, `PRODUCT_CHANGE`, `UNCANCELLATION` (and `SUBSCRIPTION_EXTENDED`):
  `plus_until` = `expiration_at_ms` (whole seconds). `NON_RENEWING_PURCHASE`, or any of those with
  no expiration: lifetime, `253402300799` (9999-12-31T23:59:59Z). `EXPIRATION`: the expiry (never
  later than now). `CANCELLATION` with `cancel_reason` `CUSTOMER_SUPPORT` (a refund): now; any other
  reason (renewal turned off) changes nothing: Plus lasts to the end of the period. `TRANSFER`: our
  users in `transferred_from` lose Plus; ours in `transferred_to` get the latest of theirs (if it
  hadn't run out). From anonymous customers there's nothing to move: the app should call
  `/me/plus/refresh` after a restore anyway. `TEST`: `result: "test"`. Anything else, or an event
  whose `entitlement_ids` doesn't include `plus`: recorded and ignored.
- A subscription event never takes away a lifetime Plus (someone with both who lets the
  subscription lapse keeps lifetime); refunding the lifetime purchase itself (no expiration) does.
- Each `event.id` counts once (`revenuecat_events`, kept 90 days): a retry answers `"duplicate"`.
  An event whose `event_timestamp_ms` is older than the last one applied to that user (or than
  their last refresh) changes nothing (`"unchanged …"`), so a late `EXPIRATION` can't undo a
  `RENEWAL`. Every answer is 200 once authorised, so RevenueCat doesn't retry what we chose to
  ignore.
- When Plus changes, the open rooms of that user's squads look at their pet again (Squad Boost's
  accessory appears or goes, priority 5).

**`POST /me/plus/refresh`**: `GET https://api.revenuecat.com/v1/subscribers/<our id>` with
`Authorization: Bearer <REVENUECAT_SECRET_KEY>`. `subscriber.entitlements.plus.expires_date`
(or its `grace_period_expires_date`, if later) becomes `plus_until`; `null` is lifetime; no `plus`
entitlement is no Plus (`plusUntil: null`). RevenueCat is the authority here: it overrides whatever
the webhook set, and webhook events from before it are then ignored. Network errors, non-2xx and
answers without a `subscriber` are 503 `try_again`, with nothing changed.

**`GET /squads`** (every squad)

- `boosted: Bool`: some current member has Plus now (Demo Buddy never does).
- `pet.accessory: Int?`: the accessory the pet wears, `1`–`6`, only while boosted; null otherwise.
  The choice is kept in D1 when the boost lapses and comes back with it.
- `streak.frozenDays: [String]`: days ('YYYY-MM-DD', the squad's zone) in the last 30, today
  included, that a freeze filled, oldest first. `streak.freezes: Int`: the caller's freezes left
  this calendar month (the squad's month today), 0 without Plus.
- `members[].isBot: Bool` (Demo Buddy, docs/launch/app-review-notes.md §3).

**Squad Boost and the pet's accessories**

- `fixtures/shop/catalogue.json` gains part `"pet"`: `pet.1` scarf, `pet.2` party hat, `pet.3`
  flower crown, `pet.4` glasses, `pet.5` bow, `pet.6` star clip; all `plus: true`, price 0. They're
  in `GET /shop` (the app's catalogue decoding must accept `part: "pet"`) but never in `owned`, and
  `POST /shop/buy` treats them like other Plus items (402 / 409): they belong to a squad, not a
  Lockling.
- `PATCH /squads/:id/pet`: any member, while the squad is boosted (the caller needn't have Plus
  themselves). `null` takes it off, boosted or not. Checks in order: 400 (not a JSON object), 403
  `not_member`, 422 `accessory_invalid` (anything but a whole number naming a `pet.<n>`, or null; a
  missing key too), 402 `plus_required` `limit: "boost"`.
- The room's `p.k` is `"<species>.<stage>.a<n>"` while boosted, at any stage (the egg too; the app
  may choose not to draw it on an egg). The server's pet-code check accepts `.a1`–`.a99`; the
  worst-case payload test still fits the 3,584-byte budget. Picking one tells the squad's open room
  at once (a priority-5 push).

**Streak freezes**

- A Plus member has 2 a calendar month, across all their squads, counted by the month of the day
  each one filled (in that squad's zone).
- When a squad's last counted day is the day before yesterday (and it has a streak), yesterday is
  filled with a freeze: a `streak_freezes` row (squad, day, member, time), and yesterday becomes
  the last counted day. The count doesn't change; today counting adds one as usual. The member is a
  person with Plus now who has a freeze left, the one with the most left, then the longest-standing.
- Checked whenever the squad is read (`GET /squads`, `PATCH`es that return it, a room refreshing
  its pet, including at the squad's midnight) and when a finished session is written (before that
  day is counted, so a finish the day after a gap carries the streak on). One gap per check: two
  missed days in a row break the streak unless a check ran in between (each check fills one).
- Concurrent checks can't freeze a day twice or spend a third freeze: each check and write is one
  statement in one D1 transaction.

**Storage**: `migrations/0007_plus.sql`: `users.plus_event_ms`, `revenuecat_events`,
`squads.pet_accessory`, `streak_freezes` (a member who deletes their account leaves the frozen day,
without them).

**Owner, server side**: the `REVENUECAT_WEBHOOK_AUTH` and `REVENUECAT_SECRET_KEY` secrets
(server/README.md, "Lockin Plus (M7)"), and the webhook URL with the same Authorization value in
RevenueCat.

## As built (app)

What the app does, settled while building it. Nothing here was run on a Mac: CI compiles and tests
it (LKKit's tests, the snapshot routes below).

**Purchases** (`Packages/LKKit/Sources/Paywall`)

- RevenueCat's SDK is `purchases-ios-spm`, `from: "5.92.0"` (released 30 September 2026; SwiftPM
  resolves the newest 5.x, 5.95.0 when this was written), product `RevenueCat`, linked by `Paywall`
  only (and `PaywallTests`). `RevenueCatPurchases.swift` is the only file that imports it, so its
  type names (it has its own `Transaction` and `VerificationResult`) never meet StoreKit's.
- The key: `LK_REVENUECAT_KEY` (empty in `Config/Shared.xcconfig`, documented in
  `Local.xcconfig.example`, written into `Local.xcconfig` by the TestFlight job from the optional
  `LK_REVENUECAT_KEY` secret) → Info.plist `LKRevenueCatKey` → `AppConfiguration.revenueCatAPIKey`
  → `PlusStore(bundleID:revenueCatKey:)`. Empty or missing: the StoreKit 2 path exactly as before
  (product ids `<bundle id>.plus.<plan>`).
- With a key, `load()` configures `Purchases` once (debug log level in Debug builds, warnings in
  Release), as the signed-in account's id or anonymous, then reads the current offering (else
  `default`): the plan is the package's type (Annual, Monthly, Lifetime), else its product id
  ending `.plus.<plan>` or `_plus_<plan>`. Prices and the trial come from the StoreKit 2 product
  behind each package (`sk2Product`), so the paywall shows the App Store's own prices and asks
  StoreKit whether the trial is on offer; RevenueCat's price strings are the fallback. Purchases,
  restores and `customerInfoStream` read the `plus` entitlement. Cancelling and Ask to Buy aren't
  errors; RevenueCat's errors map to the paywall's existing messages.
- The account: `LiveServices` hands every account change to `PlusStore.noteAccount(id:plusUntil:)`.
  RevenueCat hears `logIn(<user id>)` when the id changes, `logOut()` on signing out (skipped for an
  anonymous customer, which RevenueCat refuses), one at a time. `isPlus` = this Apple Account's
  entitlement (StoreKit's current entitlements, or RevenueCat's `plus`) **or** `plusUntil` still
  ahead on the account (lifetime is year 9999, shown as "Lifetime" in Settings).
- After any purchase or restore that went through, `PlusStore.afterPurchase` runs in the background:
  `AccountStore.refreshPlus()` → `POST /me/plus/refresh` (`LockinAPI.refreshPlus() -> User`), and
  the account takes the user it answers with. Offline or 503 it's left to RevenueCat's webhook and
  the next launch's `GET /me`. Without RevenueCat the server can't see a StoreKit-only purchase, so
  then the refresh changes nothing and Plus comes from this phone's entitlement alone.

**Squad Boost** (`API`, `Model`, `Creature`, the squad page)

- `Squad.boosted`, `SquadPet.accessory: Int?`, `SquadMember.isBot`, `SquadStreak.frozenDays` /
  `freezes`, each read tolerantly (missing or odd: false, nil, `[]`, 0). `SquadPet.code` carries the
  accessory; `PetCode` reads and writes `"<species>.<stage>.a<n>"` (1–99 kept, so a newer one round
  trips; `wornAccessory` is the one this version draws) and `PetAccessory` (in `Model`) names the
  six, `pet.1`–`pet.6`, checked against `fixtures/shop/catalogue.json`. The shop's catalogue decoding
  still skips part `pet` (they belong to a squad, not a Lockling).
- `LockinAPI.setPetAccessory(squadId:accessory:) -> Squad` (`PATCH /squads/:id/pet`, always sending
  the key, `null` to take it off) and `askDemoBuddy(squadId:) -> SessionInfo`; error code
  `accessory_invalid`, and `plus_required` with `limit: "boost"` has its own message.
- `PetView` draws the accessory as shapes (`Creature/PetAccessories.swift`): a scarf wrapped to the
  body under the mouth (clipped with `Path.intersection`), a party hat, a flower crown, round
  glasses, a bow and a star clip, sized with the stage, simpler and a little bigger below 28
  points, outlines in Always-On, never on an egg, always inside the pet's square. Where each sits on
  each species was tuned in a Python prototype of `PetGeometry` at 18, 64 and 120 points. VoiceOver
  adds "wearing a party hat". The Live Activity, widgets (`WidgetDataWriter` now writes the code
  with its accessory) and share cards draw it through the same `PetView`.
- The squad page: a "Boosted" badge under the pet's name; a "Pet accessories" grid (none and the
  six, each on the squad's own pet) for any member of a boosted squad; without the boost each tile
  wears Plus's crown and a tap opens the paywall (moment 3), as does a 402 `boost` from the server.
  An egg shows no picker (a boosted egg says it can dress up once it hatches).

**Streak freezes**: the streak row has a seven-day strip (flame counted, snowflake frozen, dashed
ring for today until it counts, grey missed), worked out by `SquadStreak.days(endingOn:)` from
`count`, `countedToday` and `frozenDays` in the squad's zone; with Plus, "N freezes left this month"
and a footer saying what a freeze does.

**Demo Buddy**: members with `isBot` show a "Test bot" label and no minutes in the week's list; a
squad with a bot has "Ask Demo Buddy to lock in" (`SquadsStore.askDemoBuddy`, which marks the room
open so Home says "Join in"). A squad with a bot doesn't count against the app's own squad limit in
Friends, matching the server.

**Paywall moments**, checked: (1) the first completed squad session offers Plus on the finished
screen once per install (`PlusMoments`); (2) a 402 from creating a squad, joining one as its 5th
member or starting a squad session opens the paywall (Friends also gates "New squad" up front); (3)
Plus Lockling parts (editor, shop), Deep Focus, Home's Custom length and the pet's accessories.
Never at launch or over a running session. Custom lengths were already in (M1): Custom opens the
5–240 minute wheel with Plus and the paywall without, Done puts the length on the tile and Lock in
starts it; if Plus ends, Home goes back to 25.

**Settings**: the Lockin Plus row says "Active", "Lifetime" or "Try free" and opens the paywall;
with Plus (not lifetime) "Manage subscription" opens the App Store's sheet
(`.manageSubscriptionsSheet`); without, "Restore purchases" (with a note when nothing was found).

**Snapshots**: `home.custom`, `squads.detail.boosted` (party hat on the teen sprout, a frozen day,
one freeze left), `squads.review` (Review Squad: Demo Buddy's label and button), `settings.plus`,

**Owner, app side** (before a TestFlight purchase can go through RevenueCat)

1. RevenueCat: create the project and its App Store app (bundle id, App Store Connect API key or
   in-app purchase key so it can read transactions), and copy the app's **public** API key
   (`appl_…`) into the GitHub secret **`LK_REVENUECAT_KEY`**. Without it TestFlight builds still
   sell Plus through StoreKit directly, but the server only learns about purchases RevenueCat sees.
2. App Store Connect: a subscription group with `<bundle id>.plus.monthly` (A$3.99) and
   `<bundle id>.plus.yearly` (A$24.99, 7-day free trial as its introductory offer), and the
   non-consumable `<bundle id>.plus.lifetime` (A$49.99); paid apps and tax/banking agreements;
   sandbox testers. The ids follow the bundle id rather than the `lockin.plus.*` above because the
   StoreKit-only path (no key) looks for `<bundle id>.plus.<plan>` (`PlusPlan.productID`, M1);
   RevenueCat goes by its packages and doesn't mind either way.
3. RevenueCat: import the three products, an entitlement **`plus`** attached to all three, and an
   offering **`default`** (made current) with packages Annual, Monthly and Lifetime.
4. RevenueCat: the webhook to `https://<api host>/webhooks/revenuecat` with the Authorization value
   in `REVENUECAT_WEBHOOK_AUTH`, and the secret key in `REVENUECAT_SECRET_KEY` (server side, above).
5. Then: a sandbox purchase on a TestFlight build should show Plus at once, and in Settings; `GET
   /me` should show `plusUntil`; a squad with that person in it should say "Boosted".

Unsure until CI compiles it: `Path.intersection` for the scarf (iOS 17 API), RevenueCat 5.x's Swift
6 sendability across `async` calls from the main actor, and the RevenueCat package resolving on the
runners (no `Package.resolved` is committed, so it takes the newest 5.x).
