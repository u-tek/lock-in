# M4 — Invites and joining

Status: **in progress** (server built, app next)

## Scope

From SPEC.md §6, §4.5 and §5.7: when someone opens a squad room, the rest of the squad gets
"Ava is locking in 🔒" with **Join 25** and **Join 50**; per-squad mute (built in M3) and quiet
hours (22:00–07:00 local by default) hold it back; it's rate-limited (SPEC.md §7, 4.5.3). Plus the
push-to-start spike (§4.5 step 3), shipped behind a developer switch until it proves reliable on
real phones.

Done when: a TestFlight phone gets the alert when a squadmate locks in, Join 25 opens the app
straight into the squad session with the Live Activity up, muted squads and quiet hours stay
silent, and the push-to-start write-up says whether to ship it.

## Server

### Who gets "is locking in"

Sent when a squad room is **opened** (the first person in; later joiners don't alert anyone),
after the response, to every other member of the squad whose:

- membership isn't muted;
- account doesn't block, and isn't blocked by, the opener;
- user isn't already in a session;
- device isn't in quiet hours in its own time zone;
- limits allow it: at most one alert per squad per recipient every 30 minutes, at most 6 a day
  per recipient across squads (rolling 24 hours), and an opener's room alerts nobody if they
  opened another room in the same squad in the last 10 minutes (open, end, open again).

Every device of each recipient gets it (sandbox or production by its `apns_env`). An APNs 410, or
400 `BadDeviceToken`, deletes the device row.

```
apns-push-type: alert            apns-topic: <bundle id>        apns-priority: 10
apns-collapse-id: lk-<sessionId> apns-expiration: now + 30 min
{
  "aps": {
    "alert": { "title": "<squad name>", "body": "Ava is locking in 🔒" },
    "sound": "default",
    "category": "LK_LOCKIN",
    "thread-id": "squad-<squadId>",
    "interruption-level": "active"
  },
  "lk": { "type": "lockin", "sid": "<sessionId>", "sq": "<squadId>" }
}
```

The name is the opener's Live Activity name (display name, else handle, else "Lockling").

### Quiet hours

`POST /devices` takes `quietHours`: `{ start, end }` as minutes after local midnight (whole numbers
0–1439, `start` ≠ `end`; `start` > `end` crosses midnight), or `null` for off. Left out, a new
device gets 22:00–07:00 (`{ start: 1320, end: 420 }`) and an existing one keeps what it has.
422 `device_invalid` otherwise.

### Push-to-start (spike)

`POST /sessions/:id/join` and `POST /sessions` take an optional
`pushToStart: { token: "<push-to-start token, hex>", env: "sandbox" | "production" }`. With it, after
joining, the server sends a push-to-start to that token and answers `Joined` plus
`"pushedToStart": true | false` (false when APNs refused or the push couldn't be built; the app
then starts the activity itself next time it's in the foreground).

```
apns-push-type: liveactivity     apns-topic: <bundle id>.push-type.liveactivity   apns-priority: 10
{
  "aps": {
    "timestamp": <now>, "event": "start",
    "content-state": <the room's state>, "attributes-type": "LockinAttributes",
    "attributes": { "sid", "me", "sq" },
    "alert": { "title": "<squad name>", "body": "You're locked in with Ava" },
    "input-push-token": 1, "stale-date": <as for updates>
  }
}
```

The activity's own update token then arrives in the app (woken in the background), which uploads
it with `POST /sessions/:id/la-token` as usual. A 410 or `BadDeviceToken` for a push-to-start
token clears `devices.push_to_start_token`.

`POST /admin/push-to-start-test` (dev only, admin token): `{ token, env }` → push-to-starts the
demo squad session (src/demo.ts) on that token, for checking from a phone without a squad.

### Storage

`migrations/0004_invites.sql`: `devices.quiet_start`, `devices.quiet_end` (nullable; both null =
off), and an `alerts(recipient_id, squad_id, sender_id, session_id, sent_at)` log for the limits,
trimmed to 2 days.

## As built (server)

Details the app relies on, settled while building the Worker (374 server tests). No shape in the
contract above changed; everything here fills in what it left open.

**"X is locking in"**

- Only `POST /sessions` opening a squad's room alerts. Joining (by `POST /sessions` or
  `POST /sessions/:id/join`) and solo sessions never do.
- Sent after the response, usually within a second. The title is the squad's name as D1 has it
  when the alert goes out; the opener's name is cut to 12 code points like the Live Activity's.
  Headers: `apns-collapse-id: lk-<sessionId>`, `apns-expiration` = now + 1800, `apns-priority: 10`,
  `apns-topic` = the bundle ID. No `mutable-content`, no badge.
- "Already in a session" means a running timer (focusing or paused) in any room, solo included.
  Someone who finished but is still in an open room isn't in a session.
- Quiet hours run from `start` up to, not including, `end`, in the phone's `tz` at the moment of
  sending. A `tz` the runtime doesn't know counts as UTC.
- Limits are per person, not per phone: one `alerts` row per person told. A person is charged only
  if at least one of their phones accepted it; someone whose phones were all quiet, all refused or
  unreachable can be told by the next room. 30 minutes means a new alert from the same squad is
  allowed 1,800 seconds after the last; "6 a day" means fewer than 6 in the 86,400 seconds before.
- The 10-minute opener rule silences the room for everyone, including members the first room
  didn't reach (they were busy or asleep). It counts rooms the same person opened in the same
  squad less than 600 seconds earlier.
- Alerts go to every registered phone not in quiet hours, whatever `laEnabled` says. A phone APNs
  calls gone (410, or 400 `BadDeviceToken`) loses its `devices` row, so the app must keep calling
  `POST /devices` on launch, as it does.
- Nothing tells the app an alert was held back (muted, quiet, limited). Without the APNs secrets,
  nothing is sent and the routes behave as before.

**Quiet hours on `POST /devices`**

- `quietHours` must be `null` or an object whose `start` and `end` are whole numbers 0–1439 and
  differ; other keys in it are ignored. Anything else is 422 `device_invalid`.
- "Existing" means the same APNs token: a phone that signs into another account keeps its quiet
  hours when `quietHours` is left out. There's no route to read them back, so the app (whose
  `QuietHours` in the App Group is the source of truth) should send them, `null` included, on
  every registration.

**Push-to-start (spike)**

- `pushToStart` is validated before anything else happens: anything but
  `{ token: <hex>, env: "sandbox" | "production" }` is 422 `token_invalid`, and nobody joins. `null`
  is the same as leaving it out. Other keys inside it are ignored; the token is stored lowercased.
- `pushedToStart` is in the answer only when the request had `pushToStart` and the join succeeded.
  Without `pushToStart` the answer is `Joined` exactly as in M3; the room's errors come back as they
  were.
- The push goes out before the answer, so the background action waits for one APNs round trip.
- Squad rooms only: a solo session answers `pushedToStart: false` (the alert needs the squad's
  name as its title). `POST /sessions` with `pushToStart` works when opening a room too.
- The alert: title = the squad's name (`attributes.sq`), body "You're locked in with Ava". It names
  the other members whose timers are running, host first: "with Ava", "with Ava and Noor", "with
  Ava and 3 others", or just "You're locked in" when nobody else is (opening). No `sound`.
- `timestamp` is the time of the request; `content-state` and `attributes` are exactly the
  `Joined` the app gets back, so the room's next update (a higher `v`) applies on top. No
  `apns-expiration`: the contract has none, so if the phone is offline APNs may deliver it late.
  Worth noting in the spike write-up.
- Joining again while already running answers the same `Joined` and sends another push-to-start,
  which could start a second activity for the same session. The app should send `pushToStart`
  only when it has no activity for that session, and end duplicates as it ends orphans.
- A 410 or `BadDeviceToken` clears `devices.push_to_start_token` wherever it equals that token;
  the app re-sends its newest one with `POST /devices` as usual. The room pushes to the activity
  only once its update token arrives with `POST /sessions/:id/la-token`.
- `POST /admin/push-to-start-test` takes exactly `{ token, env }` (other keys are 400) and starts the
  demo `squad` scenario: `attributes` `{ sid: "spike00000", me: "me00000000", sq: "Spike Squad" }`,
  body "You're locked in with Noor and 2 others". It answers like `/admin/push-test`
  (`{ status, apnsId, reason?, environment, bytes, event: "start", attributes, contentState }`, 502
  on a refusal) and is 404 under the same conditions.

**Storage and logs**

- `alerts` keeps `recipient_id` and `sender_id` as foreign keys to `users` (deleted with either
  account); `squad_id` and `session_id` are plain ids. Rows older than 2 days are trimmed whenever
  a room's alerts go out. Phones registered before 0004 have 22:00–07:00.
- Log lines, counts and session ids only: `alerts <sid>: 2 alerted, 1 in quiet hours, 0 over a
  limit; 3 pushes accepted, 0 refused, 0 failed, 0 devices removed`, `alerts <sid>: none sent (the
  opener opened another room in the last 10 minutes)`, `push-to-start <sid>: production -> APNs
  200`.

## App

- `Notifications` module: the `LK_LOCKIN` category and its actions, parsing the `lk` payload,
  quiet hours as a value (`QuietHours`, stored in the App Group defaults), and routing a response
  to what the app should do. Unit-tested.
- Join 25 / Join 50 are foreground actions: the app opens, joins the room (`POST /sessions/:id/join`)
  and starts the Live Activity. Tapping the alert itself opens Home with that squad picked, where
  "Join in" is waiting.
- In the foreground, the alert shows as a banner unless you're already in that session.
- Settings → Notifications: squad alerts on or off at the system level (opens Settings when
  denied), quiet hours on/off with From and To. Changes re-register the device.
- Spike (developer switch "Join without opening"): the actions run in the background, send the
  push-to-start token with the join, and the session engine takes up the activity iOS starts.

## Analytics

Counts only: `notificationJoin` (Join 25/50 tapped), `notificationOpened` (alert tapped),
`pushToStartJoin` (spike).

## Risks

- Background notification actions get a few seconds; joining over the network can miss it, so
  the spike may only be reliable on good connections.
- Push-to-start tokens are per app, not per activity, and change; the app saves the latest in the
  App Group so a background launch has it before ActivityKit hands it over again.
- Quiet hours depend on the device's `tz`, which is sent on every registration.
