# M4 — Invites and joining

Status: **in progress**

## Scope

From SPEC.md §6, §4.5 and §5.7: when someone opens a squad room, the rest of the squad gets
"Ava is locking in 🔒" with **Join 25** and **Join 50**; per-squad mute (built in M3) and quiet
hours (22:00–07:00 local by default) hold it back; it's rate-limited (SPEC.md §7, 4.5.3). Plus the
push-to-start spike (§4.5 step 3), shipped behind a developer switch until it proves reliable on
real phones.

Done when: a TestFlight phone gets the alert when a squadmate locks in, Join 25 opens the app
straight into the squad session with the Live Activity up, muted squads and quiet hours stay
silent, and the push-to-start write-up says whether to ship it.

## Server

### Who gets "is locking in"

Sent when a squad room is **opened** (the first person in; later joiners don't alert anyone),
after the response, to every other member of the squad whose:

- membership isn't muted;
- account doesn't block, and isn't blocked by, the opener;
- user isn't already in a session;
- device isn't in quiet hours in its own time zone;
- limits allow it: at most one alert per squad per recipient every 30 minutes, at most 6 a day
  per recipient across squads (rolling 24 hours), and an opener's room alerts nobody if they
  opened another room in the same squad in the last 10 minutes (open, end, open again).

Every device of each recipient gets it (sandbox or production by its `apns_env`). An APNs 410, or
400 `BadDeviceToken`, deletes the device row.

```
apns-push-type: alert            apns-topic: <bundle id>        apns-priority: 10
apns-collapse-id: lk-<sessionId> apns-expiration: now + 30 min
{
  "aps": {
    "alert": { "title": "<squad name>", "body": "Ava is locking in 🔒" },
    "sound": "default",
    "category": "LK_LOCKIN",
    "thread-id": "squad-<squadId>",
    "interruption-level": "active"
  },
  "lk": { "type": "lockin", "sid": "<sessionId>", "sq": "<squadId>" }
}
```

The name is the opener's Live Activity name (display name, else handle, else "Lockling").

### Quiet hours

`POST /devices` takes `quietHours`: `{ start, end }` as minutes after local midnight (whole numbers
0–1439, `start` ≠ `end`; `start` > `end` crosses midnight), or `null` for off. Left out, a new
device gets 22:00–07:00 (`{ start: 1320, end: 420 }`) and an existing one keeps what it has.
422 `device_invalid` otherwise.

### Push-to-start (spike)

`POST /sessions/:id/join` and `POST /sessions` take an optional
`pushToStart: { token: "<push-to-start token, hex>", env: "sandbox" | "production" }`. With it, after
joining, the server sends a push-to-start to that token and answers `Joined` plus
`"pushedToStart": true | false` (false when APNs refused or the push couldn't be built; the app
then starts the activity itself next time it's in the foreground).

```
apns-push-type: liveactivity     apns-topic: <bundle id>.push-type.liveactivity   apns-priority: 10
{
  "aps": {
    "timestamp": <now>, "event": "start",
    "content-state": <the room's state>, "attributes-type": "LockinAttributes",
    "attributes": { "sid", "me", "sq" },
    "alert": { "title": "<squad name>", "body": "You're locked in with Ava" },
    "input-push-token": 1, "stale-date": <as for updates>
  }
}
```

The activity's own update token then arrives in the app (woken in the background), which uploads
it with `POST /sessions/:id/la-token` as usual. A 410 or `BadDeviceToken` for a push-to-start
token clears `devices.push_to_start_token`.

`POST /admin/push-to-start-test` (dev only, admin token): `{ token, env }` → push-to-starts the
demo squad session (src/demo.ts) on that token, for checking from a phone without a squad.

### Storage

`migrations/0004_invites.sql`: `devices.quiet_start`, `devices.quiet_end` (nullable; both null =
off), and an `alerts(recipient_id, squad_id, sender_id, session_id, sent_at)` log for the limits,
trimmed to 2 days.

## App

- `Notifications` module: the `LK_LOCKIN` category and its actions, parsing the `lk` payload,
  quiet hours as a value (`QuietHours`, stored in the App Group defaults), and routing a response
  to what the app should do. Unit-tested.
- Join 25 / Join 50 are foreground actions: the app opens, joins the room (`POST /sessions/:id/join`)
  and starts the Live Activity. Tapping the alert itself opens Home with that squad picked, where
  "Join in" is waiting.
- In the foreground, the alert shows as a banner unless you're already in that session.
- Settings → Notifications: squad alerts on or off at the system level (opens Settings when
  denied), quiet hours on/off with From and To. Changes re-register the device.
- Spike (developer switch "Join without opening"): the actions run in the background, send the
  push-to-start token with the join, and the session engine takes up the activity iOS starts.

## Analytics

Counts only: `notificationJoin` (Join 25/50 tapped), `notificationOpened` (alert tapped),
`pushToStartJoin` (spike).

## Risks

- Background notification actions get a few seconds; joining over the network can miss it, so
  the spike may only be reliable on good connections.
- Push-to-start tokens are per app, not per activity, and change; the app saves the latest in the
  App Group so a background launch has it before ActivityKit hands it over again.
- Quiet hours depend on the device's `tz`, which is sent on every registration.
