# M2 — Accounts and friends

Status: **in progress**

## Scope

From SPEC.md §6 and §1.6: Sign in with Apple, a handle picker with a profanity filter, friend
codes / QR / links, a friends list, block and report, and in-app account deletion (App Review
5.1.1(v)). Accounts are optional: everything solo keeps working signed out. Signing in is offered
where friends come in: "Lock in with friends" on Home, and the card after a session.

Squads, rooms and pushes are M3. M2 only registers the device (`POST /devices`) so M3 and M4
have tokens to push to.

## API (JSON over HTTPS)

Conventions: JSON bodies and responses in camelCase; times are Unix seconds (numbers); every
route except `/auth/apple`, `/health`, `/j/:code` and `/.well-known/*` needs
`Authorization: Bearer <token>`. Errors are `{ "error": "<sentence for people>", "code":
"<machine code>" }` with the HTTP status below; the app switches on `code`, never on `error`.

```
User   = { id, handle: string|null, displayName: string|null, avatarCode, coins, plusUntil: number|null, createdAt }
Friend = { id, handle, displayName, avatarCode, since }
FriendCode = { code, url, expiresAt }
```

Rules:

- **Handles**: 3–20 characters, lowercase `a-z`, `0-9`, `_` and `.`, starting with a letter,
  stored lowercased, unique; reserved words refused. **Display names**: 1–12 code points after
  trimming (the Live Activity's `n`), no control characters. Both go through the same profanity
  check. The word list and test cases are shared: `fixtures/moderation/`, tested by the server and
  by the app's `Social` module.
- **Friend codes**: 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O, 1/I), valid
  7 days; the link is `https://<invite host>/j/<code>`, and `lockin://j/<code>` opens the app.
- **Sessions**: an opaque random token; the server stores only its SHA-256.
- **Sign in with Apple**: the server verifies the identity token against Apple's keys (issuer,
  audience = the app's bundle ID, expiry), keyed by `sub`. With the Sign in with Apple key
  configured, it also swaps the authorisation code for a refresh token so account deletion can
  revoke it, as Apple requires.
- **Deletion** removes the user's rows (friendships, blocks, codes, devices, sessions) and revokes
  the Apple token; reports they filed stay, anonymised.

## App

- Modules: `API` (REST client, Keychain token, models) and `Social` (account and friends
  stores, moderation mirror, QR codes).
- Screens: sign-in sheet (Sign in with Apple), handle picker (live availability), Friends (your
  code, QR, share link, add by code, the list with Locklings; swipe to remove, block, report),
  Settings → Account (handle, name, sign out, delete account, blocked people).
- Without a server configured (`LK_API_HOST` empty), the friends entry says friends arrive with
  the server, and nothing else changes.
- Remote notification registration (device token) and `POST /devices` after sign-in.

## Needs from the owner

- Sign in with Apple enabled on the App ID (docs/apple-setup.md step 4).
- A Sign in with Apple key (it can be the APNs key if both services are ticked) as Worker secrets
  `SIWA_KEY_ID` and `SIWA_PRIVATE_KEY`, for token revocation on deletion.
- D1 created and migrations applied (docs/apple-setup.md step 11).

## Risks

- Sign in with Apple only works on a signed build on a real phone (TestFlight); CI can't
  exercise it, so the server side is tested with a generated key and a fake Apple.
- The profanity list is a floor, not a guarantee; reports catch the rest (SPEC.md §7).
